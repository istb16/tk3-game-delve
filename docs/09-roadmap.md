# 09. 実装ロードマップ

「機能を大量に詰め込んだゲーム」ではなく「ルールは単純だが毎回違う展開になるゲーム」を目指す。
そのため **基本ループを確実に完成させてから要素を積む**。各フェーズの終わりで必ず遊べる状態を保つ。

## Phase 1 — 基本ループとドット絵 ★最優先

### Phase 1c（完了）— 回復資源

原因と経緯は [07 §7.8](07-difficulty.md)。

| 項目 | 内容 |
|---|---|
| エンティティ | 床に落ちている物（現在は Potion のみ） |

**受け入れ基準**: ✅ 達成。ドット絵のキャラが歩いて見える状態で、WASD で移動し、

## Phase 2 — 成長とループの回収 ✅ 完了

| 項目 | 内容 |
|---|---|
| パーク | レベルアップ時の 3 択（7種）。数値系は重複可、挙動系は重複させない |
| レベルアップ | 回復量を 40% に変更（ポーションが入ったので設計値に戻した） |
| アイテム | Bomb を追加。敵も壁もなければ消費しない |
| 装備 | Weapon / Armor / Ring の 3 スロット、12種。上位互換は自動、トレードオフは選択 |
| エンティティ | 宝箱 / ゴールド / 落ちている装備・アイテム |
| 派生値 | `recalcStats` がレベル・装備・パークから毎回引き直す |
| 戦闘 | クリティカル / 回避 / 吸収 / 反射 |
| 死亡 | リザルトにスコアとベスト記録 |
| 保存 | `delve.save.v1` に Best Depth / Best Score / 累計 |
| テスト | `vitest` 導入。58 件（生成・配置・ターン・アイテム・装備・成長・永続化・難易度） |
| 難易度 | 係数を二次式に変更し再測定（中央値 13、10〜15階が最多） |

**受け入れ基準**: ✅ 死んで、記録が残り、次の Run で「今回はこのビルドを試そう」と思える。

### 実測で見つけた問題（記録）

| 症状 | 原因 |
|---|---|
| 39/40 の run が測定上限 80 階に到達 | Phase 1 の係数のまま装備・パークを足したため、防御力が敵の攻撃力を追い越し被ダメージが下限1に張り付いた（→ [07 §7.3](07-difficulty.md)） |
| 中央値9・最深42階まで散る | 線形スケーリングでは序盤が厳しく深部が緩い逆S字になる。二次の項で解消 |
| `Sharpened`（+10%）を取っても数字が動かない | 割合補正の切り捨て。`floor(8 × 1.1) = 8`。四捨五入 + 最低 +1 保証に変更 |
| Swift Step で動いても視界が更新されない | `updateVisibility` をターン消費判定の後ろに置いていた |
| Ring of Vigor を拾うと他の指輪が二度と装備されない | 単一の総合スコアで順序を付けていた。支配関係だけを見て、トレードオフはプレイヤーに選ばせる形に変更 |
| 撃破ログが命中ログより先に出る | `damageEnemy` が撃破とレベルアップまで処理するのに、命中ログを後に書いていた |

## 進行ルール

- 各フェーズの終わりで **必ず遊べる状態**にしてコミットする。壊れたまま次に進まない。
- バランス数値は `src/data/` のテーブルだけを触って調整する。ロジックに数値を直接書かない。
- **バランス数値を変えたら `node tools/difficulty-model.mjs` を回し、[07](07-difficulty.md) の表を更新する。**
- 新しい敵・装備・アイテムの追加が、テーブルへの 1 エントリ追加で済む形を維持する。
  そうなっていなければ設計を直す。
- 演出は最後。ゲームプレイが面白くなる前に見た目を磨かない。
  ただし**ドット絵と歩行アニメーションは演出ではなく識別性の要件**なので Phase 1 に含める。
